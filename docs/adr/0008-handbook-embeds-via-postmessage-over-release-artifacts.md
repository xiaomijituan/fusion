# 项目三嵌入方式：iframe + postMessage 注入剧本，跨仓只走发版产物

ADR-0001 要求"嵌入方式（iframe / web component / 构建产物拷贝）另立 ADR"，这条就是那条 ADR。同时它补上一个一直没建的地基：fusion 至今没发过任何版本，而 ADR-0001 规定项目三只能依赖项目一的**发布产物**、不能 import 源码——没有发版产物，跨仓契约就是空的。决定：**章节页持有剧本 JSON，用 postMessage 注入它自己 vendor 的那份 fusion 构建产物 iframe；手册对 fusion 的一切依赖都是 release 资产，按版本号 pin 死。**

## Considered Options

- **URL fetch 加载本**（`?scenario=<url>`）：被拒。Q6 导入边界写明 v1 不做 URL fetch，且这会让模拟器去连第三方域，社区剧本的信任边界（剧本只能是数据）随之失效。
- **submodule 或复制 `src/lib/scenario.ts` 进手册仓**：被拒，直接违反 ADR-0001"只能依赖发布产物，不能 import 其源码"。复制尤其危险——fusion 改了校验规则，手册那份副本不会跟着改，坏投稿会被静默放行。
- **发 npm 包**（`@fusion/scenario` 之类）：被拒（暂时）。要占包名、要跟 fusion 的发布节奏解耦，而大陆装还要等 npmmirror 同步。release 附单文件产物是零安装、CI 里一条 curl 就能拿到的最小方案；真需要复用到别处时再补发 npm，不冲突。
- **web component**：被拒。要 fusion 额外发布并维护一个组件接口，而现在的交互需求只有一个——"把这份剧本装进去"。iframe + 一条消息就够。
- **纯静态预渲染、不做交互**：被拒。ADR-0005 已经把"一章 = 一段正文 + 一个可玩 Scenario"定成内容单元，砍掉交互等于推翻它。

## Consequences

- **注入端点是 fusion 侧唯一核心改动**，已建成（`src/lib/scenario-injection.ts` + `just-app.tsx` 的 `message` 监听）。线上形状：

  ```jsonc
  // 父页 → iframe（只这两个字段，多一个都拒）
  { "type": "fusion:load-scenario", "scenario": "<剧本 JSON 的原文字符串>" }
  // iframe → 父页（同一条消息回给发起方；不是父页发的、或本页没被嵌进来，都不回）
  { "type": "fusion:load-scenario-result", "ok": true, "errors": [], "warnings": [] }
  ```

  `scenario` 字段的值必须是一段文本，不能是已经解析好的对象。这样安排的原因是：注入不算第二条信任通道，我们收到的文本与读者手工粘贴、手工拖拽进来的文本走同一条 `importScenario()` → `parseScenario()` 路径，字段白名单和 512KB 的大小上限完全一致。如果这个页面没有被别的页面用 iframe 嵌入（也就是 `window.parent === window`），或者消息不是父页面发来的，我们既不回复也不加载。走查的第 28 到 31 项分别检查这四件事：一次合法的注入会把机房换成剧本里描述的那一间；不合格的剧本会被拒绝，机房保持原样；消息里出现规范之外的字段时，我们连剧本都不去解析；处在顶层页面时不接受任何注入。

  回执两个数组都是**已经拉平成文本的**：`errors` 是拒绝原因，`warnings` 是"装进去了但有话要说"（最要紧的一条是 `已替换同名剧本「<id>」`——库里已有同 id 的剧本会被顶掉，宿主必须听得见，否则章节页静默覆盖了读者的东西）。每条文本的形状是 `"<path>: <中文报错>"`；**报错没有路径时（整份文件的问题，比如超过 512KB 尺寸帽、JSON 解析失败）就只有文本，不带前导冒号**。

- **两个命令行产物的契约**（2026-10-07 补，之前只点名了文件、没说退出码）：

  | 产物                 | 用法                                                       | 退出码                                                                                     |
  | -------------------- | ---------------------------------------------------------- | ------------------------------------------------------------------------------------------ |
  | `scenario-check.mjs` | `node scenario-check.mjs <a.json> [<b.json> …] [--strict]` | 0 = 全部合法；1 = 有内容错误；2 = 用法错（一个文件都没给）或文件读不到                     |
  | `review-cli.mjs`     | `node review-cli.mjs <run.jsonl> [--json]`                 | 0 = 排出来了；1 = 这份文件不是合法事件流；2 = 用法错（没给文件、给了多个路径）或文件读不到 |

  两个码不要混：1 是"你交的东西不合格"，2 是"工具没跑成"——手册 CI 想按"内容不合格就红、环境没跑成也红但原因不同"来写断言，就得靠这个分界。`--strict` 只把 warning 升级成 1；`--json` 只换输出形态，不改退出码。`review-cli` **只读一个路径**，多给直接按 2 拒掉，不静默忽略。规则本体在 `src/cli/scenario-check.ts` / `src/cli/review-cli.ts`（有单测），`*-main.ts` 只做参数、读文件、打印、退出码。

- **release 资产从 v0.1.0 起固定三件**：`fusion-sim-<ver>.html`（离线单文件模拟器）、`scenario-check.mjs`（剧本校验器）、`review-cli.mjs`（事件流 → 决策表投影）。后两件是打包好的单文件，零浏览器依赖——依据是 `src/lib/review.ts` 只含两个 `import type`、`src/lib/scenario.ts` 只依赖 zod。手册 CI 按 pin 死的版本下载它们，不读 fusion 源码。**出身注释只写在两个 `.mjs` 的第 1 到 2 行**（`// fusion v<ver> … built <时间> from <sha>`），单文件 HTML 里**没有**这段注释——它的版本只能从两处外部核对：文件名上的 `<ver>`，以及这一局导出的事件流 header 里的 `appVersion`。（`v0.1.2` 前写在 ADR 与手册 `vendor/README.md` 的"文件第 1 到 3 行写着出身"是错的，那句只适用于两个 CLI 产物。）
- **`v0.1.1` 打包的还是同一批产物，只是重新发布了一次**（2026-10-08）。独立审核之后的四条修复改变了产物对外表现的行为：事件流头部那五个身份字段，检查从"字段存在就收下"改成"字段必须存在、而且类型要正确"；两个命令行工具的退出码统一成上面那张表；注入的回执多了一个 `warnings` 字段；没有路径的整份文件级错误不再带一个前导冒号。我们没有直接替换 `v0.1.0` 已经发布的文件，因为那样做会让"依赖 `v0.1.0`"这句话的含义在读者不知道的时候发生变化。手册请把版本写成 `0.1.1`，或者之后最新的 `0.1.x`。
- **`v0.1.2` 也只重发同一批产物，改的是报错文本**（2026-10-09）。手册 CI 第一次逐章跑校验器时报出一句
  `出现了规范里没有的字段（）`——括号里本该写字段名。根因在解析器：zod 的 `unrecognized_keys` 把多余字段的
  名字放在 `issue.keys` 里、`path` 留空，而解析器不分这一支，统一取 `path` 的最后一段，于是顶层的多余字段
  报成空名字，任务、主机、面板里的多余字段报成 `task` 这种作者根本没写过的词。现在顶层与三类条目都先认这一
  支，每个多余字段单独一行，路径写成 `tasks[0].bogus` 这种对着剧本就能找到的形状。判定一个字都没改（该拒的
  照样拒，`unknown_field` 与 0/1/2 那套退出码含义不变），改的是读者据此定位问题的那句话——对教学产品来说
  这句话就是产物的一部分，所以按改变对外行为处理，另起一个版本号，不替换 `v0.1.1` 已发布的文件。手册升级后
  请把 `FUSION_TAG` 与 `vendor/` 的复制件一起写成 `0.1.2`。
- **模拟器是一件自包含的 HTML，不是 zip**（2026-10-07 定）。原写"`fusion-sim-<ver>.zip`"，实现时发现：本仓的生产构建是 TanStack Start + nitro 的 SSR 产物，压根没有可直接双击的 `index.html`；而 `file://` 会拒绝加载模块脚本，散成几个文件就得靠一个本地服务器。所以另走一条 `vite.sim.config.ts`：无路由、无 SSR、无平台插件，JS 与 CSS 全部内联进一个约 395 KB（v0.1.2 实测 404,476 字节，v0.1.1 是 404,364）的 HTML，双击即起机房，除它自己什么都不取（走查 32–33 项盯着这条）。zip 只会把同一个文件藏起来，白拿一次解压。
- **iframe 装的是手册仓 vendor 的构建产物副本，不链接 fusion 官方部署站。** 否则官方站一挂，全书的交互同时失效；副本能按章节需要单独回滚。
- **兼容窗口沿用剧本格式现状**：应用接受 `schemaVersion ∈ [当前, 当前-1]`，所以手册可以落后 fusion 一个大版本而不烂。手册自身的内容格式版本另立编号，不与剧本的 `schemaVersion` 混用——先例是事件流的 `schemaVersion` 与剧本的版本互不绑定（ADR-0004）。
- **交互只在自有静态站成立，跨渠道必须降级。** 掘金与微信读书过滤 iframe 与原始 HTML，所以同一份章节正文要能编译成纯图文形态（决策表由 `review-cli` 从事件流投影而来，剧本 JSON 作为可复制文本附在文后）。这是渠道事实，不是可选优化。
- 若日后改用 web component 或 npm 包承载嵌入，需推翻本 ADR；改动面比当初直接建端点更大，所以真要换，得有新需求来证。
